# Architecture

FresherFlow is a monorepo with hard boundaries between apps. Web and mobile never touch the database; they call the API through shared wrappers. The MCP server is a thin Worker over that same API, and background work runs in a separate BullMQ process.

<DocCallout variant="tip" title="The rule of thumb">
  Frontend apps never import Prisma. They call the API through `packages/api-client`. Business rules that survive a backend rewrite live in API services or pure helpers in `packages/utils` and `packages/types`.
</DocCallout>

## Apps

- `apps/web` — public feed, company and detail pages, accounts and admin UI.
- `apps/api` — REST surface, auth, validation, business rules and queue producers.
- `apps/mcp` — AI-client surface. Every tool is an HTTP call with the caller's token.
- `apps/mobile` — candidate app with an offline feed cache.
- `apps/ingestion` — feed and job ingestion.
- `apps/api/src/worker.ts` — BullMQ processors, run as a separate process.

## Boundaries

Turborepo tags in the root `turbo.json` enforce the rules. Run `npx turbo boundaries` to check them locally; the check is advisory, not CI-blocking.

- `client-ui` packages — mobile, ui, frontend-core. They must not import `@fresherflow/database` or `@fresherflow/queue`.
- `server-only` packages — database and queue. They must not be imported by `client-ui`.
- Untagged packages — types, constants, utils and api-client are shared-neutral; both sides depend on them.

Other hard rules:

- API routes validate input, then delegate to application or infrastructure services.
- Multi-table writes use `prisma.$transaction`.
- Heavy work runs in BullMQ workers, not request handlers.
- Mobile feed data flows through `syncModule.ts` only.
- Feed regeneration starts from an admin or publish flow, never from a public frontend route.

## Data flow

### From posting to public page

1. **Discovery** — `scripts/job-discovery` finds candidate postings and writes discovery state.
2. **Processing** — `scripts/job-processor` and `apps/ingestion` turn raw postings into structured jobs.
3. **Validation** — `opportunitySchema` in `apps/api/src/utils/validation.ts` is the one listing contract. It is a closed `z.object`: unknown keys are dropped silently.
4. **Write** — every full listing write goes through `listingWrite.ts`. Payload builders live in `listingPayload.ts`.
5. **Review** — community submissions become drafts; a moderator approves or fixes and publishes them.
6. **Publish** — the publish flow regenerates the feed, bumps its version and invalidates the affected tags.
7. **Serve** — the CDN serves versioned feed files to web, mobile and the MCP public tools.

### Listing write paths

Three callers write full listings, and all three converge on the same function:

- **Admin form** — admin session — draft or published listing.
- **Draft ingester** — `INTERNAL_API_SECRET` — draft listing.
- **MCP `submit_opportunity`** — OAuth bearer — draft for users, published for moderators.

### MCP surface

`apps/mcp` resolves the caller's role from the API on each request, then registers only the tools that role may use. Account tools authenticate with the caller's own bearer token. `/mcp/public` is read-only and anonymous. See the [MCP guide](/docs/mcp).

## Caching and freshness

Public feed and category pages carry **no** ISR timer. A publish invalidates a feed tag and the next request regenerates that page once. A numeric `revalidate` would make every visitor pay for a full render.

Auth, profile, dashboard, admin, saved jobs, alerts and user-specific reads use `no-store`. Cache keys and tags use the smallest safe scope; per-user mutations never invalidate global feed tags. The only public route with a timer is `/u/[username]` at 300 seconds, because profiles have no invalidation channel.

## Security

- Parse dynamic URLs with `new URL()`; check protocol and hostname, never `includes()` on a full URL.
- Validate outbound URLs before `fetch` to prevent server-side request forgery.
- Use `crypto.randomInt` for backend randomness.
- Log detailed errors on the server; return generic client messages.
- Filter user-owned queries by `req.user.id`.
- Use `SameSite=Lax` or `Strict` cookies and validate origin or CSRF on cookie-auth mutations.
- GitHub Actions declare explicit top-level `permissions`.
- CDN and R2 URLs go through signed URL helpers; raw private object URLs are never exposed.

## Deployment

- **Vercel** — web app, with preview deployments on pull requests.
- **Render** — API and BullMQ worker, configured in `render.yaml`.
- **Cloudflare** — R2 feed storage, the CDN Worker and the MCP Worker.

The MCP Worker's `MCP_PUBLIC_URL` must match the API's OAuth resource configuration exactly; otherwise valid tokens fail verification.

CI runs lint, typecheck and build for the API and web apps, then the API test suite. After a Prisma schema change, run `pnpm db:generate` before typechecking.
