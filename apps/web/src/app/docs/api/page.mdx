# API Reference

The FresherFlow API backs the web app, the mobile apps and the MCP server. This page covers the shape of a request. The route files under `apps/api/src/routes/` are authoritative for the full list of methods and payloads.

## Base URL

<DocEndpoint value="https://api.fresherflow.in/api" />

There is no `/v1` path prefix. OAuth endpoints live at the origin root, for example `https://api.fresherflow.in/oauth/token`.

## Authentication

Sign in to get a token, then send it on every account request:

<DocEndpoint value="Authorization: Bearer <access_token>" />

```bash
curl -X POST https://api.fresherflow.in/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"you@example.com","password":"your-password"}'
```

Public routes need no token. Admin routes need an admin session and the matching permission.

## Make a request

Read your profile:

```bash
curl https://api.fresherflow.in/api/profile \
  -H 'Authorization: Bearer <access_token>'
```

List opportunities, with optional authentication:

```bash
curl 'https://api.fresherflow.in/api/opportunities?limit=20'
```

Submit an opportunity. This route requires the `opportunity.create` permission:

```bash
curl -X POST https://api.fresherflow.in/api/opportunities \
  -H 'Authorization: Bearer <access_token>' \
  -H 'Content-Type: application/json' \
  -d '{"title":"Graduate Engineer","company":"Example","jobUrl":"https://example.com/job","location":"Bengaluru","employmentType":"FULL_TIME","description":"..."}'
```

Routes for saved jobs, applications, alerts, follows, discussions and moderation follow the same pattern. See the source under `apps/api/src/routes/` for exact fields.

<DocCallout variant="note" title="MCP is not a REST endpoint">
  MCP tools are invoked over the MCP protocol at `https://mcp.fresherflow.in/mcp` with an OAuth 2.1 bearer token issued by this API. See the [MCP guide](/docs/mcp).
</DocCallout>

## Request validation

POST and PUT bodies are validated with Zod before a handler runs. The central listing schema is `opportunitySchema` in `apps/api/src/utils/validation.ts`.

<DocCallout variant="warning" title="Field names must be exact">
  `opportunitySchema` is a closed `z.object`. Unknown keys are stripped, not rejected, so a misspelled field disappears silently. Use the exact field names from the route or tool documentation.
</DocCallout>

A `Json` column such as `applicationDetails` must be set to `Prisma.DbNull`, not bare `null`, when you want a SQL NULL.

## Errors

Errors use one envelope across the API:

```json
{
  "error": {
    "message": "Validation failed",
    "details": [{ "field": "title", "message": "Required" }],
    "requestId": "req_01J..."
  }
}
```

Use the status to decide what to do: `400` fix the payload, `401` sign in again, `403` request the missing permission, `404` check the id or slug, `409` the item already exists, `429` wait and retry, `500` retry later and include the `requestId` when reporting it.

## Rate limits

Public routes, auth routes, admin mutations and the MCP surface all have rate limits. A 429 response includes `X-RateLimit-Limit`, `X-RateLimit-Remaining` and `X-RateLimit-Reset` headers. MCP and OAuth paths use dedicated per-user or per-route limiters. See [MCP rate limits](/docs/mcp#rate-limits).
