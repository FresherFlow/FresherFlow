Verdict

The sitemap has never worked. All 190 URLs in all eight sitemap files point at http://localhost:3000 — a computer that does not exist. Google cannot fetch any of them, so the sitemap has contributed nothing to discovery, while every file returned HTTP 200 and every publish run reported success.

This is not a ranking problem or a content problem. It is a discovery problem, and it sits upstream of both. No amount of on-page work reaches Google until this is fixed.

Read this first, because it changes what the rest of the report means. Most SEO problems show up in Search Console as impressions you do not have. This one does not: a sitemap full of unfetchable URLs is not an error condition, it is quietly ignored. There is no warning to look for, which is why it survived.

The technical foundations underneath it are genuinely good. Rewrite-backed sitemaps, a shared JobPosting builder, one Organization node, a 301 namespace consolidation, pixel-calibrated snippets. Someone cared about this. The failure is one environment variable being unset.

Recommendations

1. Set the public site origin on the API, and make the bad value impossible to publish

Do this

  • Set PUBLIC_FRONTEND_URL=https://fresherflow.in on the API deployment.
  • Deploy the web fix in app/api/public/sitemap/route.ts that rewrites any absolute origin inside a <loc> to the requested domain.
  • Run a publish, so the sitemaps regenerate against the real origin.

Why

  • All 190 URLs across eight files are http://localhost:3000, observed today.
  • Root cause: getPublicSiteUrl() falls back to localhost when three env vars are unset.
  • .env.example shipped those vars commented out, so a deploy built from it hits the fallback.
  • The web app could not repair it: it rewrote only the expected origin, and localhost never matched.
  • Verified: the rewrite repairs 106 of 106 URLs in the real broken file, with zero localhost left.

Two independent fixes, and both matter. The API guard stops a bad sitemap ever being written again, so the next person cannot repeat this. The web rewrite repairs the file already sitting on the CDN, so it starts working the moment the web app deploys, without waiting on a publish.

One owner action remains, and it is a deployment setting rather than a code change: set PUBLIC_FRONTEND_URL=https://fresherflow.in on the API. Without it the guard will block every publish.

Both code fixes are done. The env var is not, because it is not in the repository.

1b. Stop lying about lastmod

Do this

  • Leave <lastmod> off static routes instead of stamping today's date on each publish.

Why

  • About 20 static routes carried today's date, refreshed on every publish, so all of them claimed to change daily.
  • A crawler that learns a date field is noise stops trusting it, including the honest per-job dates.
  • Per-opportunity lastmod values come from real updatedAt/postedAt and are unaffected.

Small change, disproportionate effect: it protects the per-job dates, which are the ones worth protecting.

2. Give the site something to be found for

Do this

  • Add a /blog/[slug] route. Today /blog is one file with three hardcoded posts in an array, all sharing one URL.
  • Ship a proximity-sorted "walk-in drives near me" view on /drives/walk-in/[city].
  • Decide whether this product wants a programmatic page type competitors do not have.

Why

  • There is no post route at all, so nothing in the blog is individually addressable.
  • The geo primitives exist and go unused: walkinMapUtils.ts has lat, lng, techCluster, and a Haversine distance function. The page imports it and never calls it.
  • No linkable asset exists anywhere, so outreach has nothing to point at.
  • India-specific recruitment is a real moat: OFF_CAMPUS and POOL_CAMPUS appear in no major ATS.

The walk-in map is the interesting one. The hardest data on the site is already collected, and the surface that would use it is unbuilt. It is also the most plausible thing here to earn links, which matters more than it looks: the site currently has nothing anyone would want to cite.

A product decision, not an SEO one. Ranked second because the sitemap fix comes first, not because it matters less.

How this report was made

Made with the OpenSEO SEO Audit skill. Every finding here comes from reading the source and fetching the live CDN directly. No Search Console, ranking, volume, or backlink data was available, so no claim in this report rests on measured traffic, and nothing here should be read as a traffic forecast.

Two limits worth stating plainly. The web app returned 503 throughout, so no page could be crawled or rendered live, and the sitemap proxy could not be exercised end to end. And no credit-consuming data tool was used, so there is no Search Console, ranking, or volume data behind any claim here.

Project context was written back to OpenSEO (business overview, positioning, six competitors, fifteen key pages, and the research log) using only free tools. Credit balance after the work: 208, unchanged.

190 URLs in total, all 190 localhost. Availability checked at the time: fresherflow.in/ 503, www.fresherflow.in 503, api.fresherflow.in/health timed out, cdn.fresherflow.in 200.

Root cause, traced in source. getPublicSiteUrl() at apps/api/src/utils/runtimeConfig.ts:75 resolves PUBLIC_FRONTEND_URL || PUBLIC_WEB_URL || FRONTEND_URL, then falls back to getFallbackOrigin(3000), which is http://localhost:3000. apps/api/.env.example had lines 150 and 151 commented out, with line 15 set to localhost for local CORS. The published output proves the fallback fired.

Rewrite verification. The real broken sitemap-jobs.xml was fetched from the CDN and passed through the new rewrite: 106 URLs in, 106 out, all on the requested origin, with 0 localhost and 0 http:// remaining.

Escaping verification. The XML helper was run against Larsen & Toubro, AT&T, <script>, O'Brien, embedded newlines and tabs, and a literal &amp; to confirm no double-escaping. All well-formed, confirmed with an XML parser rather than a regex.

Header pattern verification. The (user) noindex pattern was tested against the matcher Next.js actually bundles. All 11 sections plus their children match; /jobs, /admin, /drives, /community and /u do not.

Page families read. The full (public) route tree, the root layout, robots.ts, next.config.ts, the sitemap proxy route, the API feed generator, and three existing audit documents.

What was not checked. No Search Console, so no impressions, clicks, or current ranking data. No crawl of live pages. No backlink or keyword data. No competitor comparison, because the goal in the project context is still unstated, which is why recommendation 2 is a product decision rather than a targeted keyword plan.

Competitor code review, from local clones. Ten job-board repositories under scratch/repos were read for their SEO implementation. Only freehire has a real one: a sitemap index with chunked sub-sitemaps, XML escaping, keyset pagination, and a genuine robots.txt. opensource-job-portal has a three-line robots file and no sitemap. The rest have neither. Two findings came out of it. freehire builds every <loc> from the request origin rather than configuration, which makes the localhost bug structurally impossible and is worth adopting here. It also refuses to emit a lastmod it cannot justify, which is where the lastmod recommendation above came from. Note that freehire has no origin validation and no test for one; FresherFlow now has both.
